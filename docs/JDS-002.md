# JDS-002 — Release Maintenance & Change Governance

> **Status:** active / executable  
> **Scope:** post-baseline validation, release candidates, maintenance, hotfixes, compatible improvements and breaking changes  
> **Primary invariant:** an accepted release is immutable; any functional change creates a new candidate or release identity.

## Purpose

JDS-001 governs how repositories select and execute engineering gates. JDS-002 governs what happens after a baseline or release candidate exists and testing, production use, security review or upstream change discovers that the product must change.

The standard preserves a fast conversational workflow:

```text
test
  -> observation
  -> change record
  -> implementation
  -> revalidation
  -> new candidate/release
  -> continue testing
```

An operator may simply request “correct this so we can continue”. The implementation workflow must still create or update the canonical records underneath that request.

## Authority boundary

JDS-002 owns the **transversal mechanics**:

- change classification and lifecycle;
- validation-campaign lifecycle;
- candidate/release immutability;
- SemVer/version-effect policy;
- branch strategy;
- minimum gate families by change class;
- machine-readable schemas and validation.

The product repository remains authoritative for:

- product-specific acceptance criteria;
- production promotion;
- runtime safety;
- rollback execution;
- credentials and trust boundaries;
- whether a gate result is sufficient for that product.

`repository capability != accepted artifact != deployed runtime != live support` remains mandatory.

## Release identity

### Before GA

Functional corrections during a release-candidate campaign create a new candidate:

```text
2.0.0-rc.1
  -> change
2.0.0-rc.2
  -> change
2.0.0-rc.3
  -> accepted
2.0.0
```

A candidate that changed after evidence was collected cannot reuse the old candidate identity.

### After GA

An accepted release is immutable.

| Change | Typical version effect |
|---|---|
| compatible bug/hotfix | PATCH |
| security fix | PATCH, or RC increment before GA |
| compatible hardening | PATCH or MINOR |
| compatible improvement | MINOR |
| compatibility adaptation | PATCH or MINOR |
| breaking change | MAJOR |
| documentation only | NONE |

The exact target version is a product decision, but the selected `versionEffect` must remain consistent with the class and lifecycle stage.

## Canonical change classes

- `HOTFIX`
- `BUGFIX`
- `HARDENING`
- `IMPROVEMENT`
- `COMPATIBILITY`
- `SECURITY_FIX`
- `BREAKING_CHANGE`
- `DOC_ONLY`

Avoid introducing product-specific aliases when one of these classes is sufficient.

## Change dispositions

Every discovered change receives one of three dispositions:

- `FIX_NOW` — blocks the current objective or is explicitly selected for the current release;
- `DEFER` — valid change, but not required to finish the current release;
- `REJECT` — change is not accepted for implementation.

This is the scope-control mechanism that prevents validation from turning into an endless improvement cycle.

## Change lifecycle

```text
DISCOVERED
  -> TRIAGED
  -> IMPLEMENTING
  -> VALIDATING
  -> ACCEPTED
  -> PROMOTED
  -> LIVE_VERIFIED
  -> CLOSED
```

Exceptional terminal/intermediate states:

- `BLOCKED`
- `REJECTED`
- `SUPERSEDED`
- `ROLLED_BACK`

`PROMOTED`, `LIVE_VERIFIED` and `CLOSED` are not synonyms. Repository acceptance does not imply a live deployment.

## Validation campaigns

A `ValidationCampaign` binds testing to one exact candidate identity.

Minimum identity:

- product;
- candidate version;
- exact commit SHA;
- artifact digest when an artifact exists;
- environment;
- objective.

Observations are append-only records. A required `FAIL` or `BLOCKED` observation must either:

1. remain open and prevent campaign acceptance; or
2. link to a canonical `ChangeRecord` and be resolved through revalidation.

A campaign cannot be `PASSED` while a required failure remains open.

## Proportional assurance

The central policy defines the minimum gate families expected for each class.

### BUGFIX

```text
reproduce
-> targeted test
-> affected regression
-> full regression
-> security baseline
```

### HOTFIX

```text
reproduce
-> targeted test
-> affected regression
-> security baseline
-> artifact
-> rollback
-> runtime smoke
```

### SECURITY_FIX

```text
negative security test
-> targeted test
-> full regression
-> full security assurance
-> artifact
-> rollback
```

### DOC_ONLY

```text
docs
-> links
-> secret scan
```

Products may strengthen these requirements. They may not silently remove a mandatory local product gate merely because JDS-002 classifies the change as low risk.

## Branch strategy

Default:

```text
<classification-lower>/<change-id>-<slug>
```

Example:

```text
bugfix/CHG-BRIDGE-001-approval-binding
```

Long-lived `release/<major>.<minor>` branches are created only when multiple supported release lines actually exist. A hotfix made to an older supported line must be forward-ported to `main` unless an explicit product decision records why not.

## Repository contract

A consumer may use:

```text
governance/
  release-maintenance-policy.yml

changes/
  CHG-<PRODUCT>-NNN.yaml

validation/
  VAL-<PRODUCT>-<RELEASE>.yaml
```

The central schemas are:

- `schemas/change-record.schema.json`
- `schemas/validation-campaign.schema.json`

The central validator is:

```text
scripts/validate_release_governance.py
```

## Automation contract

The intended automation is:

```text
human/test failure
  -> observation
  -> classify
  -> create/update ChangeRecord
  -> branch/PR
  -> execute proportional gates
  -> update validation evidence
  -> new candidate when required
  -> resume campaign
```

Automation must never invent a PASS, live deployment, artifact digest, approval or rollback proof.

## Adoption

Initial adoption is deliberately staged:

1. central JDS-002 policy, schemas and validator;
2. `hermes-mcp-bridge` pilot;
3. refine from the pilot without weakening evidence;
4. adopt in `m365-ui-mcp` and `hermes-security-labs`;
5. expose aggregate state to Hermes 360 without moving product authority out of the product repositories.
