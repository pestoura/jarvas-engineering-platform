# JDS-001 — Jarvas Engineering Delivery Standard

Status: **CANONICAL — v1.0**

JDS-001 defines the shared engineering and delivery contract for Jarvas/Hermes projects. It does not prescribe language, product architecture, project type, number of workers, or use of agents.

## Progression rule

```text
GREEN | PASS | SUPPORTED | ACCEPTED
                 ↓
        CONTINUE AUTOMATICALLY
```

A gate that did not execute is not GREEN.

## Core model

```text
NEXT USABLE BASELINE
        ↓
identify critical path
        ↓
small vertical slices
        ↓
bounded parallel work
        ↓
fast feedback
        ↓
integration
        ↓
required security/runtime acceptance
        ↓
version + evidence
        ↓
observe and improve
```

## Universal principles

1. Optimize for usable outcomes, not task or PR count.
2. Prefer small batches and short-lived branches.
3. Prefer vertical slices over broad unfinished horizontal foundations.
4. Establish a walking skeleton early.
5. Run cheap deterministic gates before expensive work when this improves delivery economics.
6. Bound WIP; parallelism exists only for materially independent work.
7. Treat `main` as the shared baseline and revalidate after material integration.
8. Inspect and remediate deterministic failures; never use blind retries as a strategy.
9. Make support claims only from evidence.
10. Design rollback/recovery proportional to risk.
11. Embed security in delivery.
12. Measure delivery and runtime behavior and improve from evidence.

## Definition of Delivery

```text
IMPLEMENTED
+ TESTED
+ INTEGRATED
+ REQUIRED SECURITY VALIDATION
+ REQUIRED ACCEPTANCE
+ EVIDENCE
+ OPERABILITY / RECOVERY AS APPLICABLE
= DELIVERED
```

## WIP and execution

JDS-001 does not mandate lanes or agents. In the current portfolio, active development WIP should normally remain `<= 5–6`, but the useful concurrency is the minimum implied by independent critical-path work.

A lane may be executed by a human, ChatGPT, Codex, CI automation, script, service, or external team.

For complex concurrent delivery, an **Integration Controller** role owns shared-state reconciliation, failure classification, GREEN integration, WIP control and support-claim integrity. It is a role, not an agent requirement.

## Gate ordering

Conceptually:

```text
format / syntax / compile
        ↓
static analysis / type / schema
        ↓
targeted unit tests
        ↓
contracts / docs / secrets invariants
        ↓
full tests / security analysis
        ↓
build / package / image
        ↓
integration
        ↓
live/runtime/production-like acceptance
        ↓
release / promotion
```

Not every project needs every gate. Applicable gates are selected by capability, risk and change impact. Expensive jobs should depend on successful prerequisite gates when doing so reduces wasted work without materially harming healthy time-to-GREEN.

## Failure classification

**Deterministic failure:** inspect → root cause → patch → targeted retest → continue.

**Local product failure:** isolate the affected work and continue unrelated work if the shared baseline remains safe.

**Global blocker:** stop promotion for a broken shared baseline, security-boundary failure, destructive ambiguity, cross-lane contract defect, required human/security action, critical external dependency, or insufficient evidence for a truthful support claim.

## Security baseline

Projects select applicable capabilities, including secret scanning, SCA, SAST, image scanning, SBOM/provenance, least privilege, secure defaults, trust-boundary tests and negative security invariants. Secret material must not enter source, retained evidence or model context.

## Standard / capability model

```text
STANDARD      → universal engineering principles
CAPABILITIES  → composable delivery/quality/security building blocks
PRESET        → optional convenience bundle
OVERRIDES     → project-specific additions/removals/configuration
STRATEGY      → how work is executed at a point in time
```

A preset is never a closed project category. A project may use a preset plus overrides or select capabilities directly.

## New-project declaration

Every project should declare at least:

- engineering standard;
- selected capabilities;
- risk/criticality;
- release strategy;
- acceptance requirements.

Preset and execution strategy are optional.

## Resume/recovery rule

A resumed session first reconciles live state:

```text
main + HEAD + PRs + CI + roadmap/backlog + evidence + runtime state when applicable
```

Conversation memory is advisory, not a source of truth.

## Versioning

Projects pin the engineering platform by release tag or immutable SHA and upgrade through normal PR validation. Breaking policy changes require a new JDS major version.
